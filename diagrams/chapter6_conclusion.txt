บทที่ 6
สรุปและข้อเสนอแนะ

    การดำเนินโครงงานเพื่อพัฒนาระบบเว็บแอปพลิเคชัน ระบบจองคิวซ่อมรถจักรยานยนต์และ
AI Chatbot ผู้ช่วย (THE ONE) พบว่าระบบสามารถทำงานได้ตามที่วิเคราะห์และออกแบบไว้ ทั้งในส่วน
ของการจองคิวซ่อม การจัดการงานของช่าง ระบบแชทระหว่างลูกค้ากับช่าง ระบบแจ้งเตือนอัตโนมัติ
รวมถึงระบบ AI Chatbot ที่สามารถตอบคำถามเกี่ยวกับรถจักรยานยนต์ได้ พบปัญหาและอุปสรรค
ระหว่างการพัฒนา ในบทนี้ผู้พัฒนาจึงขอสรุปความสามารถของระบบชี้แจงปัญหาและอุปสรรค
พร้อมเสนอ แนวทางในการพัฒนาระบบเว็บแอปพลิเคชัน ระบบจองคิวซ่อมรถจักรยานยนต์
และ AI Chatbot ผู้ช่วย (THE ONE) ต่อไป


6.1 สรุปความสามารถของระบบ

  6.1.1 ความต้องการของโปรแกรม (Functional Requirement)

      6.1.1.1 ผู้ใช้งานทั่วไป (ยังไม่ได้สมัครสมาชิก)
          • สมัครสมาชิก (เลือกประเภท: ลูกค้า หรือ ช่าง)
          • ลงชื่อเข้าสู่ระบบ

      6.1.1.2 ลูกค้า (Customer)
          • ดูและแก้ไขข้อมูลโปรไฟล์ของตนเอง
          • อัปโหลดรูปภาพโปรไฟล์
          • เพิ่มรถจักรยานยนต์เข้าสู่ระบบ
          • ดูรายการรถจักรยานยนต์ของตนเอง
          • สร้างการจองคิวซ่อมรถ (เลือกรถ, กรอกอาการเสีย, เลือกวันเวลานัดหมาย)
          • ดูรายการจองของตนเอง
          • ยกเลิกการจอง
          • แชทกับช่างที่รับผิดชอบงาน
          • สนทนากับ AI Chatbot สอบถามเกี่ยวกับรถจักรยานยนต์
          • ดูการแจ้งเตือนและอ่านการแจ้งเตือน
          • รีวิวให้คะแนนช่างหลังซ่อมเสร็จ
          • รีเซ็ตรหัสผ่านกรณีลืม
          • ออกจากระบบ

      6.1.1.3 ช่างซ่อม (Mechanic)
          • ดูและแก้ไขข้อมูลโปรไฟล์ของตนเอง
          • ดู Dashboard แสดงสถิติงาน (งานรอรับ, กำลังซ่อม, เสร็จแล้ว)
          • ดูคิวงานที่รอรับ (WorkQueue)
          • รับงาน (Accept) จากคิวงาน
          • ปฏิเสธงาน (Reject) จากคิวงาน
          • เริ่มดำเนินการซ่อม (Start Repair)
          • ทำเครื่องหมายงานเสร็จสิ้น (Complete)
          • แชทกับลูกค้าที่จองคิว
          • ดูการแจ้งเตือนงานใหม่และสถานะต่าง ๆ
          • ดูรีวิวและคะแนนเฉลี่ยของตนเอง
          • ออกจากระบบ

      6.1.1.4 ระบบ AI Chatbot
          • รับข้อความจากผู้ใช้และส่งไปยัง n8n Webhook
          • ประมวลผลคำถามผ่าน Google Gemini AI
          • ค้นหาข้อมูลจากฐานความรู้ด้วย PGVector (RAG)
          • ตอบคำถามเกี่ยวกับรถจักรยานยนต์จากฐานข้อมูลความรู้
          • ใช้ Fallback Response อัตโนมัติเมื่อ n8n ไม่พร้อมใช้งาน
          • บันทึกประวัติการสนทนา (ChatSession, ChatMessage)

      6.1.1.5 ระบบอัตโนมัติ (Automated System)
          • ส่งแจ้งเตือนอัตโนมัติเมื่อมีการจองใหม่ (แจ้งช่างทุกคน)
          • ส่งแจ้งเตือนอัตโนมัติเมื่อสถานะการจองเปลี่ยน
          • สร้างห้องแชทอัตโนมัติเมื่อช่างรับงาน
          • สร้าง MechanicProfile อัตโนมัติเมื่อสมัครสมาชิกประเภทช่าง
          • คำนวณคะแนนเฉลี่ยช่างอัตโนมัติเมื่อมีรีวิวใหม่
          • ป้องกันการจองซ้ำ (Duplicate Booking Detection)

  6.1.2 ความต้องการด้านคุณภาพ (Non-functional Requirements)
          • ระบบต้องสามารถตอบคำถามผ่าน AI Chatbot ได้ภายในระยะเวลา 30 วินาที
            หากเกินกำหนดจะใช้ระบบ Fallback ตอบกลับทันที
          • ระบบต้องสามารถรองรับการสมัครสมาชิกและเข้าสู่ระบบได้อย่างรวดเร็ว
            โดยใช้ JWT Token สำหรับ API Authentication
          • ระบบต้องเชื่อมต่ออินเทอร์เน็ตก่อนใช้งานทุกครั้ง
          • ระบบต้องมีการออกแบบหน้าจอที่ใช้งานง่ายและเข้าถึงฟีเจอร์ต่าง ๆ ได้อย่างรวดเร็ว
            โดยใช้ Bootstrap 5 สำหรับ Responsive Design
          • ระบบต้องมีการรักษาความปลอดภัยของรหัสผ่านของผู้ใช้งานด้วยการ hash-password
            ผ่าน Django Authentication System
          • ระบบต้องออกแบบมาเพื่อให้สามารถบำรุงรักษาและอัปเดตได้ง่าย
            โดยแยก App ตามหน้าที่ (users, booking, mechanics, chat, chatbot)
          • ระบบต้องสามารถจัดการข้อมูลฐานความรู้ AI ผ่าน Django Admin ได้
          • ระบบต้องรองรับการอัปโหลดรูปภาพ (โปรไฟล์) โดยจัดเก็บในโฟลเดอร์ที่กำหนด
          • ระบบต้องเป็น RESTful API ที่รองรับทั้ง Web View และ API Endpoint


6.2 ปัญหาและอุปสรรคในการพัฒนา

    1. ระยะเวลาในการประมวลผลของ AI Chatbot ใช้เวลานาน
       แนวทางการแก้ไข :  เพิ่มระบบ Fallback Response ที่สามารถตอบกลับผู้ใช้ได้ทันที
       เมื่อ n8n ไม่ตอบสนองภายใน 30 วินาที โดยใช้การจับ keyword จากข้อความของ
       ผู้ใช้เพื่อตอบคำตอบเบื้องต้นได้โดยไม่ต้องรอ AI

    2. ปัญหาการเข้าถึงฐานข้อมูลพร้อมกันหลายรอบ (Race Condition ในการรับงาน)
       แนวทางการแก้ไข :  เพิ่มการตรวจสอบสถานะ Booking ก่อนอนุญาตให้ช่างรับงาน
       หากช่างคนอื่นรับงานไปแล้ว จะแสดง warning และ redirect กลับ Dashboard
       ป้องกันไม่ให้ช่างหลายคนรับงานเดียวกัน

    3. ปัญหาการจองซ้ำ (Duplicate Booking)
       แนวทางการแก้ไข :  เพิ่มระบบตรวจจับ Duplicate Booking โดยตรวจสอบว่า
       ผู้ใช้เดียวกันจองรถคันเดียวกันภายในระยะเวลา 2 นาทีหรือไม่ หากซ้ำจะคืน
       Booking เดิมแทนการสร้างใหม่

    4. ปัญหาการตั้งค่าและเชื่อมต่อ PGVector สำหรับ Vector Similarity Search
       แนวทางการแก้ไข :  ติดตั้ง pgvector extension บน PostgreSQL และสร้าง
       Vector Index (IVFFlat) เพื่อเพิ่มประสิทธิภาพการค้นหาข้อมูลจากฐานความรู้
       โดยใช้ cosine similarity ในการเปรียบเทียบ embedding

    5. ปัญหาการสร้างห้องแชทอัตโนมัติเมื่อช่างรับงาน
       แนวทางการแก้ไข :  ใช้ Django Signal (post_save) ตรวจจับเมื่อ Booking
       เปลี่ยนสถานะเป็น confirmed และมีช่างรับผิดชอบ จะสร้าง ChatRoom อัตโนมัติ
       เชื่อมลูกค้ากับช่างเข้าด้วยกัน

    6. ปัญหาการนำเข้าข้อมูลฐานความรู้ (Knowledge Base) จำนวนมาก
       แนวทางการแก้ไข :  พัฒนา Script สำหรับ scrape ข้อมูลจากเว็บไซต์
       (เช่น Pantip) และแปลงเป็น embedding ด้วย Google text-embedding-004
       แล้วนำเข้าฐานข้อมูล PGVector เป็น batch

    7. ปัญหาการแจ้งเตือนแบบ Real-time
       แนวทางการแก้ไข :  ใช้ระบบ Notification ผ่าน Django Signal เพื่อสร้าง
       การแจ้งเตือนอัตโนมัติทุกครั้งที่สถานะเปลี่ยน โดยผู้ใช้สามารถดึงข้อมูลแจ้งเตือน
       ผ่าน API ที่จะแสดงจำนวน unread_count เสมอ

    8. ปัญหาข้อจำกัดของ Google API Key แบบฟรี
       เนื่องจากระบบ AI Chatbot ใช้งาน Google Gemini API (Chat Model)
       และ Google text-embedding-004 (Embeddings) ผ่าน API Key แบบฟรี
       ซึ่งมีข้อจำกัดในจำนวนครั้งของการเรียกใช้งาน (Rate Limit) และ
       จำนวน Token ต่อนาที ทำให้หากมีผู้ใช้งานพร้อมกันจำนวนมาก
       ระบบอาจไม่สามารถตอบกลับได้ทุก request หรือได้รับ error 429
       (Too Many Requests) จาก Google API
       แนวทางการแก้ไข :  หากต้องการนำระบบไปใช้งานจริงในระดับ Production
       สามารถอัปเกรดเป็น Google API แบบเสียค่าใช้จ่าย (Pay-as-you-go)
       เพื่อเพิ่ม Rate Limit และรองรับผู้ใช้จำนวนมากขึ้น หรือเปลี่ยนไปใช้
       Chat Model อื่นที่มีประสิทธิภาพสูงกว่า เช่น OpenAI GPT, DeepSeek
       เป็นต้น โดยสามารถเปลี่ยน Model ได้ง่ายผ่านการตั้งค่าใน n8n Workflow
       เนื่องจากระบบออกแบบไว้ให้ส่งข้อความผ่าน Webhook เป็นตัวกลาง


6.3 แนวทางในการพัฒนาต่อ

    จากปัญหาและอุปสรรคที่พบในระหว่างการพัฒนา รวมถึงข้อจำกัดของระบบในปัจจุบัน
    ผู้พัฒนาจึงเสนอแนวทางในการพัฒนาต่อเพื่อปรับปรุงระบบให้มีประสิทธิภาพมากยิ่งขึ้น
    ดังนี้

    1. อัปเกรด AI Chatbot ให้รองรับการใช้งานจริง (Production-ready AI)
       จากปัญหาข้อจำกัดของ Google API Key แบบฟรี (ข้อ 6.2.8) และระยะเวลา
       ในการประมวลผลที่ใช้เวลานาน (ข้อ 6.2.1) สามารถพัฒนาต่อโดยอัปเกรด
       เป็น Google API แบบเสียค่าใช้จ่าย (Pay-as-you-go) หรือเปลี่ยนไปใช้
       Chat Model อื่นที่มีประสิทธิภาพสูงกว่า เช่น OpenAI GPT, DeepSeek
       รวมถึงการ Fine-tune Model ด้วยข้อมูลเฉพาะทางด้านรถจักรยานยนต์
       เพื่อให้ตอบคำถามได้แม่นยำและรวดเร็วยิ่งขึ้น

    2. พัฒนาระบบแชทและแจ้งเตือนแบบ Real-time ด้วย WebSocket
       จากปัญหาการแจ้งเตือนแบบ Real-time (ข้อ 6.2.7) และระบบแชทที่ใช้
       HTTP Request ในปัจจุบัน สามารถพัฒนาต่อโดยเปลี่ยนเป็น WebSocket
       (Django Channels) เพื่อให้ทั้งข้อความแชทและการแจ้งเตือนแสดงผล
       แบบ Real-time โดยไม่ต้องรีเฟรชหน้า รวมถึงเพิ่มระบบ Push Notification
       ไปยังเบราว์เซอร์หรืออุปกรณ์พกพาของผู้ใช้งาน เพื่อให้ไม่พลาดการแจ้งเตือน
       สำคัญแม้ไม่ได้เปิดเว็บไซต์อยู่

    3. เพิ่มระบบป้องกัน Race Condition ด้วย Database Locking
       จากปัญหา Race Condition ในการรับงาน (ข้อ 6.2.2) ที่ปัจจุบันใช้การ
       ตรวจสอบสถานะก่อนรับงาน สามารถพัฒนาต่อโดยเพิ่มระบบ Database
       Locking (SELECT FOR UPDATE) หรือ Optimistic Locking เพื่อป้องกัน
       ปัญหาการเข้าถึงข้อมูลพร้อมกันได้อย่างสมบูรณ์ยิ่งขึ้น

    4. พัฒนาระบบนัดหมายแบบปฏิทิน (Calendar Booking)
       จากปัญหาการจองซ้ำ (ข้อ 6.2.3) สามารถพัฒนาต่อโดยเพิ่มมุมมองปฏิทิน
       ให้ลูกค้าและช่างสามารถเห็นตารางนัดหมายที่ว่าง เพื่อลดปัญหาการจอง
       ซ้อนกันในวันเวลาเดียวกัน และช่วยให้ช่างจัดการตารางงานได้สะดวกขึ้น

    5. ขยายฐานความรู้ AI และปรับปรุงระบบ RAG
       จากปัญหาการนำเข้าข้อมูลฐานความรู้จำนวนมาก (ข้อ 6.2.6) และการ
       ตั้งค่า PGVector (ข้อ 6.2.4) สามารถพัฒนาต่อโดยเพิ่มแหล่งข้อมูล
       ฐานความรู้ให้หลากหลายมากขึ้น เช่น คู่มือซ่อมอย่างเป็นทางการจากผู้ผลิต
       และปรับปรุง Vector Index ให้ใช้ HNSW แทน IVFFlat เพื่อเพิ่ม
       ความเร็วและความแม่นยำในการค้นหา

    6. การรองรับการใช้งานจากอุปกรณ์พกพา (Mobile Application)
       พัฒนาแอปพลิเคชัน Mobile ด้วย React Native หรือ Flutter เพื่อรองรับ
       การใช้งานบนสมาร์ทโฟนและแท็บเล็ต โดยเชื่อมต่อกับ REST API ที่มีอยู่
       ทำให้ลูกค้าสามารถจองคิว แชท และรับแจ้งเตือนได้สะดวกยิ่งขึ้น

    7. เพิ่มระบบการชำระเงินออนไลน์และจัดการค่าใช้จ่าย
       พัฒนาระบบชำระเงินผ่าน PromptPay, บัตรเครดิต หรือ Mobile Banking
       เพื่อให้ลูกค้าสามารถชำระค่าบริการผ่านแอปพลิเคชันได้โดยตรง รวมถึงให้
       ช่างสามารถเพิ่มรายการอะไหล่และค่าใช้จ่ายในแต่ละงาน เพื่อความโปร่งใส

    8. เพิ่มระบบรายงานและสถิติสำหรับผู้ดูแลระบบ (Admin Dashboard)
       พัฒนา Dashboard สำหรับผู้ดูแลระบบเพื่อดูสถิติการใช้งาน จำนวนผู้ใช้
       จำนวนการจอง รายได้ คะแนนรีวิว และประสิทธิภาพของ AI Chatbot
       เพื่อประกอบการตัดสินใจและปรับปรุงระบบอย่างต่อเนื่อง
